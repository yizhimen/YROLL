# YROLL v0.2 Foundation Reality Audit → 精确补洞

> 本文为三轮审计的收敛版：凡是后面被推翻/修正的判断，只保留最终结论。
> 原始逐轮记录见 `v0.2 Foundation Reality Audit → 精确补洞.原始版.md`。

---

## 0. 一句话结论

**YROLL 现在最大的风险不是 Frame，而是 Mutation Gate。**

Frame 那边只是"架构尚未收敛"；而 Lease / Revision 这边已经出现了**真实的 bypass**——有些 HTTP mutation 有 revision 检查，有些完全没有；`/mutation/check` 存在，并不意味着 mutation 自动受它保护。这件事应该优先修。

不需要重做 YROLL。现在的任务是：**把已经存在的几套半成品语义，收敛成一条唯一的编辑路径。**

## 2. P0-01 Frame First：Frame API ≠ Frame Editor

架构原则已经写对了：`Internal canonical time is frames, not seconds.`
并且已有 `Rational` / `FrameTime{frame:int, fps:Rational}` / `FrameRange[start, end)` / `Timebase`——这部分设计是对的，保留。

但实际模型没迁过去：

```
Clip.source_range: TimeRange      # float seconds
Clip.timeline_range: TimeRange    # float seconds
Shot.start / end: float
```

CommandLayer 主 API 仍是 seconds-native：

```python
def add_clip(asset_id, source_start: float, source_end: float, timeline_start: float)
    → TimeRange(start=source_start, end=source_end)
```

测试自身就是证据：

```python
c = layer.add_clip_frame("fa", 0, 60, 0)
assert c.timeline_range.end == 2.0   # 60 frames → 2.0 sec
```

代码里甚至直接写明 `Frame-based add_clip. Internally converts to seconds.`

所以现在的路径是：

```
Frame → _frame_to_sec() → 旧 seconds mutation
```

**Frame API 现在是 Adapter，不是 canonical。**

### 明确禁令
**不要再增加 `*_frame()` API**（`split_clip_frame()`、`ripple_frame()`…）。继续加只会固化"旧 seconds API + Frame API"两套并存。

正确方向：
```
Frame → Canonical Edit Model → Command
seconds 仅作为 UI / ffmpeg / import / export adapter
```

## 3. P0-02 TimeMap：最明确的缺口

现有 `timebase.py` 只能做 `FrameTime.from_seconds()` / `.to_seconds()`（用了 Rational FPS，这点是好的）。但真正需要的是：

```
Source Frame → Clip Local Frame → Timeline Frame
```

例：source 12,000；clip source=10,000~13,000；timeline=1,500~4,500
→ source 12,000 → clip local 2,000 → timeline 3,500

**Time Mapping 不是没有代码，而是没有成为基础设施。** 它已经被手写实现了好几遍：

- `generate_subtitles()`：`tl_s = tr.start + (s - sr.start) / clip.speed`
- 填充词删除：又自己做了一套 source → timeline 映射

一旦加入 reverse / speed ramp / slip / freeze / nested sequence / transition，这里会彻底失控。

### 目标对象
```
TimeMap:
  source_frame  → clip_frame
  clip_frame    → timeline_frame
  timeline_frame → source_frame
考虑：trim / speed / slip / reverse
后续：nested sequence / transition / freeze
```

Agent 才能问："Timeline 第 1832 帧对应原视频哪一帧？" → `asset A, source frame 2214`。

### 首批测试选型
**不要用普通 move/trim 做 TimeMap 的第一批测试，用「字幕映射 + speed + trim」**——这能最快暴露映射层设计是否正确。

speed 是 TimeMap 的关键用例：30fps / source 101 frames / speed 1.5x → timeline 是 67 帧还是 67.333？必须由 TimeMap / Frame policy 决定。**speed 不能最后才迁移。**

## 4. P0-03 Selection：模型保留，集成未通

已有独立 `@dataclass Selection`，支持 single / multi / range / track，含 `intersects()` / `contains_clip()` / `contains_track()`，测试覆盖完整。**不要推倒重做。**

但文件顶部的注释就暴露了现实：`every mutation should accept it instead of just clip_id`——说明还没做到。

```
Selection object       ✅
Selection tests        ✅
FrameRange selection   ✅
Selection HTTP/MCP     🟡
Selection → mutation   🔴
Multi-selection edit   🔴
Range selection edit   🔴
Track selection edit   🔴
```

目标 API：`move(selection, delta_frames)` / `trim(selection, ...)` / `delete(selection)`，且内部**不能**退化成 `for clip_id: move_clip(...)`。

## 5. P0-04 Mutation：现在真正的战场

### 5.1 不推倒，用 MutationContext 收敛
不需要另起一个巨大的 Mutation Engine。CommandLayer / Operation / ProjectCore / undo-redo 已经是 Mutation Engine 的雏形，架构方向正确（validate → before/after → modify → log Operation；GUI/Agent/MCP 调用同一套 Command API）。

正确做法是在现有 CommandLayer 上加：

```
MutationContext
├── actor
├── session
├── base_revision
├── selection
├── timebase
└── reason

Command → MutationContext → validate → plan → apply → Operation → commit
```

### 5.2 核心时间线 mutation 现状

| Mutation | 时间语义 | Selection | Frame | Operation | 评价 |
|---|---|---|---|---|---|
| add_clip | seconds | ❌ | Adapter | ✅ | 🟡 |
| remove_clip | seconds | ❌ | ❌ | ✅ | 🟡 |
| ripple_delete_clip | seconds | ❌ | ❌ | ✅ | 🟠 |
| trim_clip | seconds | ❌ | Adapter | ✅ | 🟡 |
| split_clip | seconds | ❌ | Adapter | ✅ | 🟡 |
| move_clip | seconds | ❌ | Adapter | ✅ | 🟡 |
| set_speed | seconds | ❌ | ❌ | ✅ | 🟠 |

当前 CommandLayer 内部实际是两代系统并存：

```
              CommandLayer
             /            \
    Legacy commands       Frame commands
      seconds                frames
      clip_id                clip_id
```

这就是最需要消灭的东西。

### 5.3 Operation 不是完整事务

`ripple_delete_clip()` 思路已经很好（删除 → 同轨后移 → Semantic Link 找 strong relationship → 跨轨字幕/音频同移 → 记录一个 Operation）。**不要推倒，应该升级。**

但它暴露结构问题：真正被改的对象塞在 `before.shifted` / `before.cross_shifted` 里，redo 靠 `old_start / dur / shifted / cross_shifted` 反推。能工作，但应该明确成：

```
MutationPlan
  primary:  delete clip X
  effects:  shift clip A -12 frames
            shift clip B -12 frames
            shift subtitle C -12 frames
  operation: atomic
```

这样 Agent 执行前就能看到"删除这个镜头会影响 7 个对象"——这就是 Preview / Impact。

### 5.4 Composite Mutation 必须原子化

**正式规定：一个用户/Agent 意图 = 一个 Atomic Operation。**

- `remove_silence`：检测 silence → keep ranges → 原 clip 改成第一段 → 创建 N 个新 clip → 重排 track
- `remove_filler_words`：ASR words → 找 filler → source→timeline → 合并 → 删原 clip → 创建多个新 clip
- `ripple_delete`
- `replace_clip_voice`：**最典型的 atomicity bypass**

```python
# replace_clip_voice 现状
self.add_clip(...)        # → Operation A
self.set_muted(...)       # → Operation B
self.core.save_state()    # ← 在最终 Operation 之前就落盘
return self._record("voice_replace")   # → Operation C
```

应改成：
```
voice_replace
 ├── create asset
 ├── add generated audio clip
 ├── mute original
 └── ONE Operation
```
或建立真正的 Transaction / MutationBatch，并**禁止内部随意 `save_state()`**。

### 5.5 Undo/Redo
ProjectCore 已有相当完整的 undo/redo，但是按 op_type 写的一大串 if/elif 恢复器。这**不是** P0-04 必须马上重构的东西，但必须确保：**所有新的 frame-native mutation 都能产生可逆的 Operation**，否则会变成"编辑按帧、Undo 回到 seconds 逻辑"。

### 5.6 seconds 边界
`removed_seconds`、`min_word_dur: float` 等媒体分析结果用 seconds 本身没问题。真正的问题是**分析结果进入编辑内核时必须转成 frame**——现在还没有这个边界。

## 6. Mutation Gate：真实存在的 bypass（最高优先级）

### 6.1 Revision bypass
**有** `sessionId` / `baseRevision` 保护的：`add_clip`（sessionId → `require_edit_right()`；baseRevision → `check_project_revision()`）、`trim`、`split`、`move`。

**没有任何保护**的：
```
speed, volume, adjust, silence-remove, denoise, delogo,
transform, color, flip, opacity, crop, reverse, fade, dissolve
```
全部直接 `guard(lambda: st.cmd.xxx(...))`。

也就是说现在是"**部分 mutation 有 Revision**"，而不是"**Mutation Engine 有 Revision**"。

### 6.2 Track mutation 完全没有 Gate
```
POST /tracks
POST /tracks/{id}/mute
POST /tracks/{id}/lock
POST /tracks/{id}/hide
```
直接 `st.cmd.add_track(...)`，没有 sessionId / require_edit_right / baseRevision。

### 6.3 `/mutation/check` 的性质
它是一个 **endpoint，不是 mutation middleware**。它的存在不构成保护。

### 6.4 `require_revision()` 是死代码
server 里有 `def require_revision(fn):` 但没有完成真正的检查逻辑；实际用的是 `_check_rev(...)`。应清掉或统一，否则以后会被误认为"系统已经统一"。

### 6.5 Chat Agent 是第二条未受保护的编辑路径
HTTP 与 WebSocket chat 都是：
```python
task = Task(CommandLayer(st.core, who=Actor.AI), ...)
result = task.run(...)        # 或 task.apply_actions(...)
st.core.save_state()
```
看不到 Lease / Revision gate。必须验证：**人持有 Edit Lease 时，Agent Chat 能不能绕过 Lease 修改工程？**

现状 vs 目标：
```
现状：                          目标：
        AI                              AI
       /  \                            /  \
   HTTP    Chat Task              HTTP     Chat
     │        │                     └───┬───┘
  部分Gate  CommandLayer                ▼
     └────┬────┘                  Mutation Gate
          ▼                        Lease + Revision
       Project                           ▼
                                      Command
                                         ▼
                                     Operation
                                         ▼
                                      Project
```

### 6.6 四类 bypass 汇总
1. Legacy seconds mutation 仍可直接修改工程
2. 高级 Command 内部调用其他 Command + 自行 `save_state()` + 自己记 Operation（`replace_clip_voice`）
3. Chat Task → CommandLayer → save_state，未经 Lease/Revision
4. HTTP endpoint → `guard()` → Command；若 `guard()` 只做异常处理而非统一 gate，即为绕过

## 7. 施工顺序（最终定死）

> 早期版本曾建议 P0-02 → P0-01 → P0-03 → P0-04；**审计后已修正为下述顺序**——Gate 优先。

### P0-04A｜Mutation Gate（第一步，先不要碰 Frame）
所有 mutation 统一经过 `require_edit_right()` + `check_project_revision()`。
不允许调用方用 `sessionId=""` 绕过。**编辑请求必须携带 mutation context。**

### P0-04B｜Atomic Mutation
解决 `replace_voice` / `silence_remove` / `filler_remove` / `ripple_delete`：一个用户意图 = 一个 Operation，禁止内部随意 `save_state()`。

### P0-02｜TimeMap
建立 SourceFrame / ClipFrame / TimelineFrame 的 canonical mapping。

### P0-01｜真正 Frame-native
把 trim / move / split / ripple / speed 从 seconds 迁到 frames，**而不是继续增加 `*_frame()` adapter**。

### P0-03｜Selection integration
Selection → Mutation 真正贯通。

### 之后
Frame-native Mutation → Selection-native Editing → **Timeline GUI Reality Test**（"我坐下来能不能像剪映一样剪？"）

## 9. 最终评级

**🟢 保留，不要动**
`Operation` / `CommandLayer` / `Undo-Redo` / `Selection model` / `FrameTime`+`FrameRange` / `Lease store`（acquire, release, heartbeat, handoff, conflict）/ `Revision model`

**🟡 必须迁移（seconds-native）**
`add_clip` `trim` `split` `move` `remove` `ripple_delete` `speed` `subtitle generation`

**🟠 必须升级为 Atomic Composite Mutation**
`ripple_delete` `remove_silence` `remove_filler_words` `replace_clip_voice`

**🔴 必须修 Gate（无统一 Lease + Revision enforcement）**
track mutations / visual mutations / audio mutations / `speed` / `adjust` / `silence remove` / AI Chat

## 10. 目标架构

```
              GUI / Agent / MCP
                       ▼
                  Selection
                       ▼
                   TimeMap
                       ▼
           Frame-native Command
                       ▼
               Mutation Plan
             ┌─────────┴─────────┐
          Impact              Operation
             └─────────┬─────────┘
                       ▼
                  ProjectCore
                       ▼
              Revision + Lease
                       ▼
                     State
```

真正的交互终点：
```
鼠标拖动 → Frame → Snap → Selection → Mutation → Impact → Operation → Revision → Preview
```
而不是：`鼠标拖动 → 0.133 sec → 某个 JS 算法 → 后端再换成 frame`。
